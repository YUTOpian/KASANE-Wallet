# DAO（symbol_book_v3_demo_dao の移植）

サービス → 「DAO」から使えます（Symbol・秘密鍵のプロファイルと SSS Extension のプロファイル。閲覧用 / Ledger では出ません）。

## 元アプリとの違い
元アプリは「サーバーの秘密鍵（master）」が手数料を立て替え、アグリゲートを作って署名し、ハッシュロックを払っていました。
この移植ではサーバーを使わず、**ウォレットで開いているアカウントがその役を自分で行います**。

| 元アプリ | ここ |
| --- | --- |
| サーバーが master で署名・発行 | 開いているアカウントが発行者として署名 |
| SSS で連署 | 同じアカウントの署名に含まれる（管理者が複数なら、他の管理者は「マルチシグ」の署名待ちから連署） |
| 管理者が1人でも bonded + ハッシュロック | 管理者の署名だけで足りるなら complete（ハッシュロック不要）。足りなければ bonded |
| 会員の投票・テーマ保存は master が手数料を肩代わり | 会員が自分の手数料を払う |
| 管理者の追加・削除（DAO設定） | 「DAO設定」の中で、既存の「マルチシグの設定変更」のフォームをそのまま使う（画面は移らない。同意の署名・承認数・多段にも対応） |

## SSS Extension で使うとき
- 署名は SSS Extension で行う（確認画面で「確認」を押すと、拡張の画面に署名の依頼が出る）。他の SSS 対応の画面と同じ仕組み（`lib/symbol/sssSign.ts` の `signWithAny`）。
- 署名の回数: 通常は 1 回。他の管理者の連署が要る形（bonded）は、アグリゲートとハッシュロックの 2 回。投票の作成は 2 段階なので、その分も増える。
- DAO の作成のとき、作ったばかりのアカウントの連署は、SSS の署名が入ったあとで付ける（連署のハッシュは発行者の署名を含むため）。`lib/dao/daoTx.ts` の `signDaoWith` / `addTempCosignatures`。
- 「DAO 設定」の管理者の追加・削除・承認数の変更は、「DAO設定」の中に埋め込んだ「マルチシグの設定変更」のフォーム（`MultisigConvertEmbedded`、`account` にDAOのアドレスを渡す）で行う。画面は移らない。SSS でも使える（署名は拡張で行う）。
- 他の管理者として署名待ち（bonded）に連署することも、SSS でできる。拡張にはアグリゲートのバイト列が要るが、ノードは中身を JSON でしか返さないので、JSON から組み立て直して渡す（`lib/symbol/partialPayload.ts`）。組み立てたものがノードのハッシュと一致しなければ、拡張に頼まずに止める。対応しているのは DAO とマルチシグで使う種類（送金・マルチシグの変更・メタデータ3種・モザイクの定義/増減/回収）。それ以外を含む署名待ちは「秘密鍵で開くプロファイルで連署してください」と出す。

## 画面（/dao, /dao/create, /dao/view?id=<DAOの公開鍵>&tab=…）
ホーム / ガバナンス投票 / ポイント交換 / 特別会員限定 / （管理者のみ）DAO設定・特典管理・ポイント管理。

## オンチェーンの形（元アプリと同じ）
- DAO = マルチシグのアカウント。メタデータ: key5 = ガバナンストークンID、key1〜4 = 投票箱A〜Dの公開鍵、key8・9 = 投票箱E・Fの公開鍵（選択肢は最大6つ。以前に作ったDAOには無く、E・Fを使う投票を作るとき登録のアグリゲートで書き足す）、key6 = DAO名、key99〜 = 投票の索引（作成トランザクションのハッシュ）。
- ポイント = 譲渡不可・回収可、特典 = 譲渡不可・回収不可（モザイクメタデータ name / type）。交換アイテム = 特典のモザイクメタデータ（exchangeable / description / pointMosaicId / pointMosaicName / exchangeCost）。
- 投票 = 投票ごとに専用トークンをガバナンストークンの保有者へ配り、会員が選択肢の投票箱へ送る。票の重みは投票ごとに選べる: 重み付けあり（保有量と同じだけ・既定）/ なし（1 人 1 票）。なしのときだけ、索引メッセージ（JSON）に `weighted: false` が入る。5・6つ目の選択肢は `e`・`f`、投票の期限は `end`（UTC のミリ秒）が入る（どちらも使うときだけ。無ければ4択・期限なし）。期限を過ぎた投票は、画面からは投票できず、期限のブロックより後に投票箱へ届いた分は集計から除く。作成者が「締め切る」と、残りの投票トークンを回収して使い捨てのアドレスへ送り、投票トークンに `voteClosed = 1` のメタデータを付ける（これでチェーン上でも投票できなくなる）（無ければあり。元アプリの形式のまま読める）。投票できるのは、いまガバナンストークンを持っている人だけ（画面で確認。投票トークンだけ受け取っても投票できない）。

## ガバナンストークンの配布・ネームスペースの紐付け（「ポイント管理」「特典管理」）
- 「ポイント管理」の先頭に、ポイントとは別枠で「ガバナンストークン」が出る。会員へ配る（宛先はアドレス入力。会員が 0 人でも配れる）/ 回収できる。
- ガバナンストークン・ポイント・特典それぞれに「ネームスペース」ボタン。DAO が持っているネームスペースを紐付けるか、新しい名前（ルートは日数分のレンタル、子は親が DAO のもの）を作って紐付ける。署名者は DAO。レンタル料は DAO アカウントが払い、足りなければ同じアグリゲートでウォレットから入金する。
- 紐付けたネームスペースは一覧と、「ポイント交換」の特典・ポイントの選択にモザイク ID の代わりに表示される（紐付けが無ければ ID）。

## ネームスペースの期限（「ネームスペース」タブ・管理者のみ）

- 「ネームスペース」タブに、DAO アカウントが持つネームスペースを有効期限つきで一覧にする（期限切れ → 期限が近い順 → 無期限、子は親のすぐ下）。1か月以内は「期限が近い」、切れていれば「期限切れ」の印が付く。紐付け先（ガバナンストークン・ポイント・特典の名前）も出る。
- ルートの行の「更新」で、日数を指定して延長する。Symbol に専用の更新トランザクションは無いので、DAO（持ち主）が同じ名前でルートをもう一度登録して、今の期限に期間を足す。署名は DAO、レンタル料は DAO アカウントが払い、足りなければ同じアグリゲートでウォレットから入金する。期限切れでも、猶予期間のうちは同じ操作で更新できる（過ぎて他の人が取っていれば失敗する）。
- サブネームスペースの期限は親と同じなので、更新ボタンは親の行だけ。残りと合わせた期間は最長 1825 日まで（ウォレットの更新画面と同じ規則）。
- 警告: ガバナンストークン・ポイント・特典の紐付けの表示と、ネームスペースの紐付け画面の「いま紐付いている名前」の下に、期限が1か月以内（黄）・切れている（赤）ときに警告が出て、「更新へ」ボタンでこのタブに移る。期限切れの名前を入れたときのエラーにも同じボタンが付く。DAO が持つルートが見つからない名前（他のアカウントのもの）には出さない。
- コード: `lib/dao/daoNamespaceExpiry.ts`（判定）、`lib/dao/daoActions.ts` の `planRenewNamespace` / `composeRenewNamespace`、`pages/dao/DaoNamespaces.tsx`（タブ）、`pages/dao/DaoNamespaceWarning.tsx`（警告）。テストは `dev-tests/dao-namespace-expiry.test.ts`。
- `lib/dao/daoApi.ts`（`fetchMosaicNamespaceNames` / `lookupNamespace`）、`daoActions.ts`（`planLinkNamespace`）、`pages/dao/DaoNamespace.tsx`、`dev-tests/dao-namespace.test.ts`。

## 会員が多いとき（1 回の操作で最大 1000 人・1000 件）

1 つのアグリゲートに入る内側のトランザクションは 100 件まで（ネットワークの決まり）。配布・回収・投票の作成は、宛先を **100 件ずつに分けて、アグリゲートを何回かに分けて送る**。1 回の操作で扱える数の上限は `MAX_DAO_ITEMS`（1000）。

- **配布・回収**（ガバナンストークン・ポイント・特典）: `planSendMosaicBatches` / `planRevokeBatches` が 100 件ずつの計画に分け、`submitDaoBatches` が順に送る。1 回ずつ独立している。管理者の連署が要る形なら、1 回ごとに bonded（ハッシュロックと連署がそれぞれ要る）。管理者の署名だけで足りるなら、すべて complete。
- **投票の作成**: 1 回目に「索引・モザイク定義・供給量」の 3 件が入るので、1 回目は 97 人、2 回目以降は 100 人ずつ（1000 人なら 11 回）。ウォレットのアカウントだけの署名で済む（complete）。順番は ①1 回目を送って**確定を待つ**（以降の配布は投票トークンが要る）→ ②残りの配布 → ③**最後に** DAO のメタデータへ索引を登録（管理者の連署が要るなら bonded）。索引の登録が最後なので、途中で止まった投票は一覧に出ない。`submitCreateVote`。
- **途中で止まったとき**: 1 回目が確定したあと、再開に必要なもの（投票トークン ID・1 回目のハッシュ・重み付け・タイトル）を、この端末のブラウザ（localStorage、DAO ごと）に残す。「ガバナンス投票」の作成欄の上に「途中で止まった投票」が出て、「続きから再開」で、ガバナンストークンを持っているのにまだ投票トークンを受け取っていない会員**だけ**に配って、最後に索引を登録する（`planResumeVote` / `submitResumeVote`。受け取り済みかは投票トークンの保有者で見る）。手元の投票トークンが足りなければ止める。索引に登録済みなら記録は自動で消える。
- **配布・回収が途中で止まったとき**: 送れた回数までは取り消せない。確認画面に「何回目まで送信したか・先頭から何件は送信済みか」が出る。やり直すときは、送信済みの分を除く（除かないと重ねて送ってしまう）。
- 確認画面は、宛先が 20 件を超えると先頭の 20 件と「ほか N 件」だけを出す。複数回に分かれるときは、回数・（SSS Extension なら）署名の確認が出る回数・連署が要る回数も出る。
- SSS Extension のプロファイルは、分けた回数だけ署名の確認が出る（秘密鍵のプロファイルはパスワード 1 回）。
- 会員一覧の取得（`fetchHolders`）は 1 ページ `PAGE` 件ずつのページ送りで、集計（投票箱の保有量を読む）は人数に影響されない。
- コード: `lib/dao/daoBatch.ts`（`MAX_DAO_ITEMS`・`chunk`・`submitDaoBatches`・`submitCreateVote`・`submitResumeVote`・再開用の記録）、`lib/dao/daoActions.ts`、`pages/dao/daoUi.tsx`（進み具合・確認画面）、`DaoMosaics.tsx`、`DaoGovernance.tsx`。テストは `dev-tests/dao-batch.test.ts`（1000 人の分割・重複なし・再開・記録）。

## ページに入る条件（「DAO設定」）
管理者は「DAO設定」で、DAOのページに誰が入れるかを選べる。
- **DAOのIDだけで入れる**（既定）: IDを控えていれば誰でも入れる（これまでと同じ）。
- **IDとガバナンストークンの両方が必要**: ガバナンストークンを1つ以上持っている人だけ入れる。持っていない人には、入れない理由・トークンID・自分の保有量だけの画面が出る。管理者は、トークンが0でも常に入れる。
- 設定は DAO アカウント自身のアカウントメタデータ key 7（値 `id` / `token`）。署名者は DAO（管理者の連署）。`fetchDao` は「DAO 自身が付けたもの」だけを読む（管理者が自分の名前で同じキーを付けても無視する）。読み込みに失敗したときは開かずにエラーにする。
- 入れなかった DAO は「最近開いた DAO」に残さない。
- これはウォレットの画面で入れるかどうかを決めるもので、ブロックチェーン上の情報（メタデータ・保有者など）は誰でも読める。
- `lib/dao/daoCore.ts`（`DaoAccess` / `parseDaoAccess` / `canEnterDao`）、`daoApi.ts`（`DaoInfo.access`）、`daoActions.ts`（`planSetAccess`）、`pages/dao/DaoFrame.tsx`（入口の判定）、`DaoSettings.tsx`、`dev-tests/dao-access.test.ts`。

## 自動連署ボット（ポイント交換・サーバー専用）
「ポイント交換」は、会員の申請（DAO がポイントを回収して特典を送るアグリゲート）に管理者が連署して成立する。サーバーで KASANE Wallet を動かすときだけ、**この連署を自動で行うボット**を別プロセスで動かせる。起動しなければ、従来どおり管理者が手動で連署する（ウォレットの画面・動きは変わらない）。

### 有効になる条件
- `KASANE_DAO_BOT=1` を付けて `npm run dao-bot` を起動したときだけ働く。付けなければ「無効」と出して終了する。
- ボットのコードは `src/server/` にあるが、ウォレットの画面からは誰も読み込まないので、ビルド（`dist/index.html`）には入らない（`tsconfig.app.json` でブラウザ向けの型チェックからも外してある）。秘密鍵はサーバーの中だけに置く（画面には出ない）。
- `file://` で開く・GitHub Pages に置く、などの静的な使い方では動かない（動かす場所がない）。

### 準備
1. ボット専用のアカウントを新しく作る（ほかの用途と共用しない。XYM は連署に要らないので、ほぼ 0 でよい）。
2. DAO 設定の管理者の追加（既存の「マルチシグの設定変更」のフォーム）で、そのアドレスを連署者に加える。承認数が 1 なら、ボットの連署だけで交換が成立する。2 以上なら、ボットのほかに管理者の連署も要る（ボットは自分の分だけ連署する）。
3. サーバーに環境変数を設定して起動する（`.env.example` を参照）。まず `KASANE_DAO_BOT_DRY_RUN=1`（判定だけ・連署は送らない）で試すとよい。

起動時に、ボットが DAO の連署者に入っているかを確かめ、入っていなければ理由を出して止まる。

### 連署するもの / しないもの
連署するのは、`planRequestExchange` が作る形の申請**だけ**。次をすべて満たさなければ連署しない（`src/server/dao-bot/verify.ts`）。
- ノードの JSON から組み立て直したアグリゲートのハッシュが、ノードの言うハッシュと一致する（`lib/symbol/partialPayload.ts`）。
- 内側がちょうど 2 件（DAO がポイントを回収 → DAO が特典を送る）。
- 申請した人 = ポイントを回収される人 = 特典を受け取る人（メッセージなし、宛先はアドレス）。
- 特典がチェーン上で交換アイテムになっていて（DAO 自身が付けたメタデータ）、回収するポイントの ID と量が `pointMosaicId × exchangeCost × 数量` とぴったり一致する。
- 申請した人のポイントと、DAO の特典の在庫が足りている（足りないときは、いまは連署せず、次の回に見直す）。
- （任意）`KASANE_DAO_BOT_MAX_QTY` を超えない。

管理者の設定変更・配布・回収・投票の索引など、ほかの署名待ちには連署しない（ボットのコードに、それらに連署する経路はない）。

### 注意
- ボットは DAO の連署者なので、**ボットの鍵が漏れると、承認数しだいで DAO を操作される**。鍵のファイルの権限を絞り（600）、専用のアカウントを使い、承認数・管理者の構成を見直すこと。高額な特典が多いときは、`KASANE_DAO_BOT_MAX_QTY` で 1 回の数量を絞るか、ボットを使わず手動の連署のままにする。
- 連署するのは、ボットが動いている間だけ。止まっている間の申請は、再開したときにまとめて処理する（期限切れのものはノードから消える）。管理者が手動で連署してもよい（先に成立したほうが有効。ボットが後から送った連署は無視される）。
- 画面: 管理者が開く「DAO設定」の下に「自動連署ボット（サーバー専用）」の案内がある（`pages/dao/DaoBotGuide.tsx`。手順・コピーできる環境変数・「ボットを管理者に追加する」ボタン）。ボットが動いているかは、画面からは分からない。「ポイント交換」の説明文にも、ボットを使うDAOでは自動で署名される旨を足してある。表示はメインネット / テストネットだけ。
- コード: `pages/dao/DaoBotGuide.tsx`（案内）、`src/server/dao-bot/verify.ts`（判定）、`src/server/dao-bot/run.ts`（起動・監視・連署の送信）、テストは `dev-tests/dao-bot.test.ts`（`npx tsx dev-tests/dao-bot.test.ts`）。
